# 配置可靠性增量治理设计

## 目标与边界

本阶段处理配置一致性、恢复可靠性、批量请求压力和终端文本安全，不引入系统 Keychain、数据库或新的服务层。根据使用偏好，本机终端中的 Token 保持完整显示，包括 `list`、`current`、创建摘要和供应商详情；分享导出继续默认移除 Token，只有 `--include-secrets` 才写入密钥。成功标准是：所有配置在加载、保存和恢复前经过同一结构与语义校验；单文件更新不会产生半写文件；批量检查存在明确并发上限；Token 或模型变化不会复用旧状态缓存；备份文件名不会碰撞；错误信息不会执行终端控制序列。

## 架构与数据流

沿用现有 CommonJS 单体 CLI。`import-validator` 扩展为共享配置验证边界，根据 `local` 与 `import` 两种来源应用不同策略：本地配置允许用户主动保存最高权限参数，外部导入仍拒绝；两者共享字段类型、名称、URL 和当前供应商一致性校验。新增 `atomic-file` 工具，在目标文件同目录写临时文件、同步并原子重命名，供主配置、导出文件、Codex 文件和 Claude settings 复用。恢复流程改为“读取 -> 校验/标准化 -> 备份当前配置 -> 原子保存 -> 刷新内存状态”。状态检查使用 Token SHA-256 指纹和模型生成缓存键，并通过固定大小 worker pool 控制并发。

## ADR：选择增量共享工具而非 ConfigRepository 重构

选择增量方案，因为当前模块已具备清晰调用入口，新增两个小工具即可消除主要失败模式，改动和迁移风险可控，符合 KISS 与 YAGNI。完整 `ConfigRepository` 能进一步落实 SOLID，但会同时改写约 700 行配置管理和多条命令链路，不适合与尚未提交的安全加固合并。代价是 Codex 的两个文件仍是“各文件原子、跨文件非事务”；现有修改前备份继续作为恢复保障，真正跨文件事务留给后续独立版本。

## 测试策略

测试覆盖默认完整 Token 输出、错误配置加载不覆盖原文件、原子写入失败清理临时文件、恢复前拒绝无效备份、同秒备份唯一、5 MB 文件与 200 个供应商上限、Token/模型变化导致缓存失效、最大并发数，以及 ANSI/双向文本转义。最终执行 ESLint、Prettier、全量覆盖率、生产依赖审计和 npm 打包预检。
